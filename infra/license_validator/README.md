# IFA License Validator (BEAAA-569)

Stub implementation of the Path 3 (design-partner PyInstaller binary) license
gate per ADR-0011 §3.4. Consumed by BEAAA-567's binary at every invocation.

* **Contract:** `contracts/are-scanner-api-v1.md@v1.1.0` — no contract delta;
  this is internal IFA infra.
* **Classification:** rule-change (new IFA-hosted dependency for Path 3).
* **CTO co-sign ref:** BEAAA-562 ADR-0011 rev 2 accepted 2026-05-19T15:03:37.879Z.
* **Status:** stub landed (BEAAA-569). Production hardening (real TLS,
  KMS-backed signing keys, audit-log retention, on-call) is a follow-on
  child filed after BEAAA-567 clears its smoke against this stub.

## What this is

A FastAPI app exposing two routes:

| Route | Auth | Caller |
|---|---|---|
| `POST /license/validate` | none (public; license-key is the credential) | the design-partner binary on every scan invocation |
| `POST /license/revoke`   | `Authorization: Bearer <admin_token>` | IFA admin (CBDO/CTO) for in-field revocation |
| `GET  /healthz`          | none | load balancer / smoke |

Validation outcomes (BEAAA-569 §4, exhaustive):

* `valid`              — returns a short-lived Ed25519-signed attestation
* `revoked`            — key revoked OR unknown (collapsed on the wire to
  prevent enumeration; the audit log records `unknown_key` separately)
* `expired`            — key past its `expires_at`
* `partner_mismatch`   — request `partner_id` or `binary_build_id` does not
  match the key's issuance record
* `binary_blacklisted` — `binary_build_id` is on the admin blacklist

The binary fails closed on every non-`valid` outcome (BEAAA-567 §3.4 / §4).

## Layout

```
infra/license_validator/
  attestation.py   # Ed25519 sign/verify of compact attestation tokens
  registry.py     # file-backed key registry (atomic JSON writes)
  audit.py        # append-only JSONL audit sink
  service.py      # pure validate() — transport-agnostic kernel
  app.py          # FastAPI surface for the two routes above
  client.py       # reference client the binary imports
  cli.py          # admin CLI: init-keys, issue, revoke, list, blacklist-build, serve
  README.md       # this file
```

Tests: `tests/test_license_validator.py` (23 cases — five contract
outcomes, three BEAAA-567 §6 negative smokes, attestation security).

## Quick start (local dev)

```sh
cd projects/are-scanner

# 1. Generate the signing keypair (once per environment).
python -m infra.license_validator.cli init-keys \
  --private-key /tmp/lv/private.pem \
  --public-key  /tmp/lv/public.pem

# 2. Issue a license to a design partner.
python -m infra.license_validator.cli issue \
  --registry /tmp/lv/registry.json \
  --partner-id partner-acme \
  --binary-build-id build-2026-05-19-linux-amd64-acme

# 3. Run the service.
python -m infra.license_validator.cli serve \
  --registry    /tmp/lv/registry.json \
  --audit       /tmp/lv/audit.log \
  --private-key /tmp/lv/private.pem \
  --admin-token "$(openssl rand -hex 32)" \
  --host 127.0.0.1 --port 8731

# 4. From another shell, validate.
curl -s http://127.0.0.1:8731/license/validate \
  -H 'Content-Type: application/json' \
  -d '{
    "partner_id": "partner-acme",
    "binary_build_id": "build-2026-05-19-linux-amd64-acme",
    "scan_id": "scan-0001",
    "timestamp": "2026-05-19T16:00:00Z",
    "license_key": "<lk_... from step 2>"
  }'
```

## Signing-key management

* **Algorithm:** Ed25519. Selected over RSA for compact public keys (32 B raw
  vs ≥256 B for RSA-2048) — the public key is embedded in the binary at
  build time (BEAAA-567 §3.7) and Ed25519 keeps the binary lean.
* **Storage in stub:** PEM file on disk, mode `0600`, generated by
  `cli.py init-keys`. **Not suitable for production.**
* **Storage in production (hardening child, separate ticket):** key material
  lives in a managed KMS (AWS KMS / GCP KMS) with sign-only access; only the
  PEM-encoded *public* key ships into the binary.
* **Rotation cadence:**
  * Routine: every 90 days. Generate a new keypair; ship a new binary
    bundling the new public key to active design partners; revoke old
    keys at the end of the grace window.
  * Emergency (suspected private-key compromise): generate immediately;
    blacklist every binary build that ships the compromised public key
    (`cli.py blacklist-build`); cut new binaries for all active partners;
    revoke old keys.
* **Embedding into binary build:** BEAAA-567 §3.7 + §7 gate 3 own this.
  Build pipeline reads the current public-key PEM at PyInstaller time and
  bakes it into the binary alongside the corpus. The public key is *not*
  mixed into the canonical `corpus_snapshot_hash` (ADR-0011 §3.5 — that
  hash stays canonical so calibration is byte-identical across distribution
  modes).
* **Compromise detection:** the audit log (`source_ip`, `partner_id`,
  `binary_build_id` clusters) feeds anomaly detection in the hardening
  child. Off-pattern usage (geography, volume, off-hours) triggers Founder
  escalation per ADR-0011 §6.

## Attestation token format

Compact, no third-party JWT dependency:

```
<base64url(payload_json)>.<base64url(signature)>
```

Payload (canonical JSON, sorted keys, separators `(",", ":")`):

```json
{
  "binary_build_id": "...",
  "expires_at": "ISO-8601 UTC",
  "issued_at":  "ISO-8601 UTC",
  "key_id":     "sha256(public_key_raw)[:16]",
  "partner_id": "...",
  "scan_id":    "..."
}
```

The binary's verifier (`client.fetch_attestation` →
`attestation.verify_attestation`) checks:

1. Signature validates against the embedded public key.
2. `key_id` matches the public key's fingerprint (pins the build to a
   specific signing key; a rotated key requires a new binary).
3. `partner_id` and `binary_build_id` match the binary's own identity.
4. `expires_at > now` (TTL has not lapsed).
5. `issued_at <= now + 5min` (clock-skew tolerance).

TTL is clamped server-side to ≤24h (`attestation.MAX_TTL` per ADR-0011 §3.4).

## Audit log

Append-only JSONL at the path passed to `cli.py serve --audit`. One line
per `POST /license/validate` call. Schema (BEAAA-569 §6):

```json
{
  "timestamp": "ISO-8601 UTC",
  "partner_id": "...",
  "binary_build_id": "...",
  "scan_id": "...",
  "source_ip": "...",
  "outcome": "valid | revoked | expired | partner_mismatch | binary_blacklisted | unknown_key",
  "key_id": "..."
}
```

No transcript content, no scored output, no PII (ADR-0011 §6 boundary).

Retention is **90 days** (matches BEAAA-552 design-partner retention horizon).
Rotation is not automatic in the stub; production hardening replaces the
file sink with a managed log target.

## Revocation runbook

In-field wall-clock revocation target: **≤10 minutes** per ADR-0011 §10
option (2). Per-binary effect is bounded by the unexpired attestation TTL
(≤24h worst case, instant if a fresh validation is required for the next
scan invocation — fail-closed, no offline grace per ADR-0011 §3.4).

1. **Decision.** Founder or CTO authorizes revocation. Reason is recorded
   in plain text on the revocation call.
2. **Execute.**
   ```sh
   python -m infra.license_validator.cli revoke \
     --registry /path/to/registry.json \
     --license-key lk_... \
     --reason "partner offboarded — CBDO 2026-06-30"
   ```
   *Or* call `POST /license/revoke` with the admin Bearer token. Both paths
   write to the same registry and are idempotent.
3. **Confirm.** Next `POST /license/validate` for that key returns
   `{"outcome": "revoked", "attestation": null}`; the binary fails closed.
4. **Optional: blacklist the build.** If the binary itself must stop scoring
   regardless of any future key, also blacklist the `binary_build_id`:
   ```sh
   python -m infra.license_validator.cli blacklist-build \
     --registry /path/to/registry.json \
     --binary-build-id build-2026-05-19-linux-amd64-acme
   ```

Phase-wide rollback (stop building new binaries; let outstanding keys
expire at `expires_at` default 2026-06-30) is ADR-0011 §10 option (3) and
does not need any action against this service.

## Production hardening — explicitly out of scope here

Filed as a follow-on child to BEAAA-569 once BEAAA-567's smoke clears
against this stub. Scope of the hardening child:

* TLS termination at a documented host (the design-partner binary must hit
  `https://...` not `http://`); cert rotation.
* KMS-backed signing key (replace the PEM-file private-key flow in
  `attestation.load_private_key`).
* Transactional store for the registry (replace `registry.Registry`'s
  JSON file with a real DB; the public record shape stays identical).
* Managed log target for the audit log + 90-day retention rotation.
* On-call rotation + alerts on the anomaly detection hooks named in
  ADR-0011 §6.
* Real admin auth (replace the static Bearer token with SSO + role check).
