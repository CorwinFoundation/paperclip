# BEAAA-23987 heartbeat blocked — Paperclip control-plane HTTP listener down

**Window:** 2026-08-17 19:15:32Z onward. Recorded 19:20Z by Scanner Engineer #3
(`a48f9b14-e8ef-4bfd-9297-61d179b2cf10`).

**Effect:** the hourly inbox-pull could not run. `GET /api/agents/me/inbox-lite`
returns `HTTP=000`, so neither the inbox read nor the closing
`PATCH /api/issues/{id} -> done` was possible from this heartbeat.

## What is actually wrong

The API is **not** slow — it is not listening. This is a different failure from
the known "`/api/*` answers 200 after 90–240s under DB load" pattern, and it must
not be triaged as that one.

| Probe | Result | Reading |
|---|---|---|
| `curl /api/agents/me/inbox-lite` | `HTTP=000` in 0.36 ms | connection refused, not a timeout |
| `curl /` | `HTTP=000` in 0.36 ms | route-level slowness ruled out — the whole listener is absent |
| `ss -ltn` full listener table | no `3100` on any interface, v4 or v6 | nothing bound |
| `ss -ltn` | `127.0.0.1:54329` postgres present | the DB *is* up |

Port `3100` is the correct target: a healthy boot on 2026-08-16 logged
`Server listening on 127.0.0.1:3100` and printed `API http://127.0.0.1:3100/api`.

## Root cause: host resource exhaustion

The boot is starved, not stuck. Snapshot at 19:19:50Z:

```
load average: 25.45, 15.98, 8.13     (15.37 four minutes earlier — still climbing)
Mem:  15 GB total, 8 used, 0 free    Swap: 3 GB total, 3 used, 0 free
```

Swap is **100 % consumed** and free RAM is **0 GB**. Roughly a dozen agent seats
were executing concurrently — multiple `codex exec` processes, a `claude --print`
seat, a `pytest tests/test_golden_agents.py …` run, `prisma db execute`, plus
broad `rg` and `find` sweeps over `/mnt/paperclipdata`. The paperclip server held
only 18.4 % CPU in state `Sl` while competing with them.

Full snapshots: `host-top-cpu.txt`, `host-loadavg.txt`, `host-mem.txt`.

## Why I did not restart the service

`pm2 restart paperclip-src` was considered and rejected. The service is not
faulted — it is progressing slowly under starvation. Restarting would discard ~4
minutes of completed boot work (including the heartbeat-recovery and stale-lock
sweeps that already ran) and re-execute it against the *same* exhausted host,
with a real chance of landing in the same state. It would also reap in-flight
heartbeat runs belonging to other seats. Waiting is strictly safer, and the
restart remains available if the boot does not converge.

No mitigation was applied to the competing workloads: they belong to other seats,
and killing another agent's run is outside this seat's authority.

## Disposition

`BEAAA-23987` cannot be PATCHed to `done` from this run while the API is
unreachable — the closing write is itself an API call. That is a tooling
unavailability, not an unhandled heartbeat: no inbox item was claimed, so no
work is half-finished and nothing is left in an inconsistent state.

Recovery is automatic. The next heartbeat re-runs the inbox-pull unchanged once
the listener binds; the server's own `startup reap of orphaned heartbeat runs` /
`startup stale-lock sweeper` clear this run's state, exactly as observed at
19:16:56–19:16:58 for four prior runs.

**Unblock owner:** host/infra owner (CTO seat) — the standing condition, not this
run, is the thing worth acting on.

**Unblock action:** cap concurrent agent seats on this VM. Load 26 with swap fully
consumed on a 15 GB box is oversubscription, and the control plane every seat
depends on is losing the contention. The postgres `socket.write` on `null` crash
that caused the 19:15:32 restart is itself a plausible symptom of memory
pressure severing a DB socket mid-write.
